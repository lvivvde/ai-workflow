# 文档证据查询政策

本政策适用于通过 `game-design-knowledge` MCP 查询游戏策划文档、配置表和图片资料的所有回答。

## 核心原则

AI 只能依据 MCP 返回的已索引文档证据回答。模型常识、项目外知识、名称相似度和未经确认的语义联想均不得作为项目事实。

## 强制规则

1. 只能使用已索引文档、配置表和已确认术语表中的事实。
2. 禁止根据名称相似、行业惯例、模型记忆或玩法常识推断项目中存在某个功能。
3. 查询词没有证据时，必须回答“当前已索引文档中未找到”，不得推荐或映射到相似玩法。
4. 文档只描述部分规则时，只能陈述已记录部分，并明确列出未记录内容。
5. 多份文档冲突时，必须列出冲突内容及各自出处，不得自行选择正确版本。
6. 只有文档明确说明时才能陈述设计意图；禁止根据配置数值、界面图片或实现结果反推意图。
7. 每个项目结论必须带文件路径，以及章节、段落、工作表、行、列或单元格等可用定位信息。
8. 索引过期时必须提示；不得将过期索引无条件表述为当前事实。
9. 禁止自动创建玩法别名。只有文档明确记载或用户明确确认后，别名才能成为授权知识来源。
10. 用户明确确认的别名必须保存到独立、可审查的事实文件，不能只存在于可重建 SQLite 索引中。

## 允许行为

- 摘要文档明确写出的内容。
- 将多个证据片段整理为步骤，但不得补充缺失步骤。
- 汇总方案、配置和图片的明确事实。
- 报告证据之间的一致、缺失或冲突。
- 使用语义检索发现候选证据，但最终结论必须由明确证据支持。

## 禁止行为

- 将相似名称判断为同一玩法。
- 根据行业常见设计补充项目规则。
- 根据数值配置猜测策划目的。
- 将视觉模型对图片的描述当作设计意图。
- 在没有证据时用“应该”“通常”“可能是”补全答案。
- 未经确认记录或使用玩法外号、简称和历史名称。

## 未找到时的回答

```text
当前已索引文档中未找到“<查询词>”对应的玩法或已确认别名。

这不代表项目一定不存在该玩法，只表示当前文档证据不足。
```

## 回答结构

```text
结论
文档事实
证据出处
未记录或不确定内容
冲突信息（如有）
索引状态
```

## 别名确认

以下情况可以记录别名：

- 文档明确写明正式名称与简称的关系。
- 用户明确表达“以后 X 指 Y”“X 就是 Y，请记录”等确认语句。

AI基于相似度提出的猜测不是事实，不得自动记录，也不得在文档查询回答中作为映射使用。
